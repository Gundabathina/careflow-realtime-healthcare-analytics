# Security

## Synthetic data, by design

Every record in this project -- patients, encounters, conditions,
claims, everything -- is generated by [Synthea](https://github.com/synthetichealth/synthea).
No real patient data has ever been used, stored, or displayed anywhere
in this repository. See [`docs/data_ethics.md`](data_ethics.md) for the
full discussion of what that does and doesn't mean for how the data
should be interpreted.

## PII discipline, enforced as if the data were real

Even though the data is synthetic, the project enforces PII exclusion
rules throughout, as a matter of engineering discipline (and because
the same code paths would need to be safe if ever pointed at real
data):

**Never exposed in any public model, dashboard, or export:** SSN,
passport number, driver's license number, patient first/middle/last
name, street address, precise latitude/longitude.

**Enforced at four independent layers**, so no single mistake could
leak one of these fields:

1. **Gold layer** -- `dim_patient` drops these fields before anything
   downstream ever sees them (`docs/gold_layer_guide.md`).
2. **dbt layer** -- a macro (`dbt/macros/pii_guard.sql`) checks
   `information_schema.columns` for restricted-PII-looking column names
   on every public mart, enforced by a dedicated test
   (`no_restricted_pii_in_public_models.sql`).
3. **Dashboard** -- `dashboard/database.assert_no_restricted_columns`
   independently blocks any query result carrying a restricted column,
   even if a future query author's mistake selected one.
4. **Power BI exports** -- audited in `powerbi/data_dictionary.md` and
   verified by `tests/test_powerbi_exports.py`.

**What's safe and shown:** patient surrogate keys (no name/SSN
attached), age *group* (never exact age or birth date), gender, race,
ethnicity, marital status, city/state/county/ZIP (synthetic, so this
carries no real-world privacy risk), provider and organization *names*
(operational/business identifiers, not patient PII -- expected on a
provider performance page exactly as they would be in a real hospital's
BI tooling).

## Secrets management

- **PostgreSQL and Airflow credentials are environment variables only.**
  Every component reads them through
  `careflow.warehouse.postgres_client.load_connection_config()` -- there
  is no second, divergent credential-loading path anywhere in the project.
- **`.env` is never committed** (`.gitignore`); `.env.example` ships
  only placeholder values, explicitly labeled as local-development-only
  and requiring real values for anything beyond that.
- **Airflow's Fernet key and webserver secret key** are generated per
  deployment (commands documented in `.env.example`), passed only via
  environment variables into the containers, never written to a
  committed config file (`airflow/config/airflow.cfg.example` is a
  reference file with no secrets in it -- the live config is entirely
  env-var driven).
- **Errors are sanitized before they reach a log or the UI.** A raw
  driver exception can embed a connection string; every layer that
  might surface one (dashboard queries, dbt runs, Airflow task/callback
  logs) passes it through a `sanitize_text`-style redaction function
  first (password= patterns, embedded DSN credentials, and the literal
  configured password value, all replaced with `***`).
- **No credential is ever passed as a CLI argument.** Every subprocess
  call in this project (`scripts/run_dbt.py`, `scripts/start_airflow.py`,
  the Airflow custom operator, etc.) reads credentials from the
  inherited process environment, never from `argv` -- so a credential
  can never show up in a process list or a logged command line.

## Dashboard-specific restrictions

- Every SQL query in `dashboard/queries.py` uses `%s` parameter
  placeholders -- filter values are never string-interpolated into SQL
  text. The one exception (a column *name*, not a value) is the
  readmission-window selector, which resolves through a fixed
  `{7: ..., 14: ..., 30: ...}` dict, never the raw filter input.
- CSV downloads are built from the same PII-checked query results
  rendered on screen -- there is no separate export code path that
  could bypass the restricted-column check.
- Database errors shown in the UI are always the sanitized
  `DashboardQueryError`, never a raw psycopg exception.

## Reporting safety

Pipeline quality reports (`reports/`) are generated from real pipeline
runs and are tracked in the repository as evidence of verified results
-- they contain aggregate counts and pass/fail statuses only, never
row-level patient data.

## Reporting a security issue

This is a portfolio project with no production deployment or real user
data; there is no formal security disclosure process. If you notice a
genuine issue in the PII-handling or credential-handling logic
described above, open a GitHub issue describing it.
